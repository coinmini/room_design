# AI 室内设计 MVP 优化计划

> 审计日期：2026-08-04 ｜ 审计范围：V0.6 全栈（FastAPI + React）
> 方法：6 个维度并行源码审计 → 逐条对抗性验证 → 归并综合
> 结果：54 条经验证发现（另有 8 条被推翻），归并为 **17 个根因**

---

## 0. 起因与实测数据

**用户反馈**：生成图片速度慢，客户需要等几分钟才能看到生成的效果。

审计从 `.local/artifacts/floorplan-kuyao-final-*` 的文件 mtime 反推了 **77 次真实 provider 调用**的间隔分布：

| 分位 | p10 | p25 | p50 | p75 | p90 |
|---|---|---|---|---|---|
| 单张生成延迟 | 58s | 64s | **91s** | 174s | 277s |

两个关键推论：

1. **尾部延迟很重**（p90 是 p50 的 3 倍）。串行耗时 = N 次调用之和；并发耗时 = **max-of-N**，不是均值。因此并发化的真实收益是 **2.5–3 倍**，而不是朴素估算的 N 倍。
2. 在观测到的劣化区间（一次真实 9 图任务，间隔 213–333s），**12 张串行 = 50+ 分钟**，直接击穿前端 30 分钟超时。并发化是把这个区间拉回超时内的唯一手段。

**各阶段批量规模**（源码确认）：

| 阶段 | 处理函数 | 变体数上限 |
|---|---|---|
| 03 彩平图 | `run_ai_color_plan` | 4 |
| 04 轴侧概念图 | `run_ai_axonometric` | 3 |
| 05 分空间效果图 | `run_ai_space_render` | **12** |
| 06 风格方案 | `run_ai_style_scheme` | 3 |
| 07 色调方案 | `run_ai_tone_scheme` | 3 |

## 1. 最高杠杆改动：并发扇出 + 增量发布

**作为一个 PR 提交。** 两项改动落在同样的五个循环体上，拆开做等于改两遍。

### 改动内容

- **文件**：`apps/api/app/processors/ai_workflow.py:427, 497, 605, 803, 879`；`apps/api/app/jobs.py:31, 77, 84`；`apps/web/src/AiDesignWorkflow.tsx` 约 20 行
- **做法**：把每个循环体抽成 `_generate_one(index, item) -> dict`，用 `ThreadPoolExecutor(max_workers=4)` + `as_completed` 驱动；每完成一张，通过短生命周期 `SessionLocal()` 回调把增长中的 `outputs` 写回 `job.result`；终态写入前按原始 index 排序保证确定性

### 用户实际感受

| 指标 | 现在 | 改后 |
|---|---|---|
| 彩平 N=4 总耗时 | ~365s | ~120–190s |
| 分空间 N=12 总耗时 | 12–19 分钟 | 3–5 分钟 |
| **首图可见时间（所有阶段）** | **N × 91s** | **~60–90s** |

首图时间是真正的杠杆点。客户 90 秒看到第一张，而不是 10 分钟后一次性看到 12 张。

**工作量**：约 1 天（含前端 gating）

### 本 PR 内必须一并处理的三个坑

漏掉任何一个都会引入新 bug：

1. **`batchStatus` 误报**。`_base_result`（`ai_workflow.py:367`）在无失败时写 `batchStatus: "complete"`，`BatchNotice`（`AiDesignWorkflow.tsx:762-769`）会在批次中途弹出「✓ 本批次全部生成完成」。partial 写入必须强制 `batchStatus: "running"`。
2. **审批按钮提前暴露**。部分结果会让「设为批准彩平」（`AiDesignWorkflow.tsx:966-980`）在 `ensure_scene_asset`（`jobs.py:89`）执行前就可点击，批准会落进无 `assetId` 分支。**审批/基线类按钮必须 gate 在 `job.status === 'SUCCEEDED'`。**
3. **JSON 列不可原地修改**。`job.result` 是 SQLAlchemy JSON 列，必须整体重新赋值。代码库已在 `jobs.py:90` 注明这一点。

### 为什么 `n>1` 批量参数救不了

每次循环迭代构造的 prompt 都不同（`ai_workflow.py:428-436, 498-512, 609-629`），而 OpenAI edits 接口的 `n` 语义是「同一 prompt 出 k 个样本」。线程并发是唯一可行解。

## 2. (A) 直接削减真实耗时

### A1 — 即第 1 节的并发扇出

A 类的价值几乎全部集中在这里。

### A2 — 共享连接池 + 拆分超时 ⚠️ 必须先于或同时于 A1 落地

`kuyao_image_edit.py:481` 每张图新建 `httpx.Client`。`http_client` 参数和 `owns_client` 守卫（`:480/:502`）已存在，但只有测试在用。

实测对真实网关：TLS appconnect **冷 0.96–1.23s，热 0.000s**。

- 单独看只占 365s 批次的 **0.5% 以下——不要把它当作提速手段**
- 但并发化后，它决定了是 4–12 个同时握手还是复用连接

同一改动里把 `kuyao_image_edit.py:177` 和 `:354` 的裸 float 换成
`httpx.Timeout(connect=5, read=timeout_seconds, write=120, pool=10)`，
并把 `kuyao_image_timeout_seconds`（`config.py:34`）从 **900 降到 180–300**。
今天网关不可达会让一个任务挂满 **15 分钟**才失败。`floorplan_vision.py:597` 同样处理。

**工作量**：约 1 小时

### A3 — 重试退避 + 并发信号量 ⚠️ 依赖 A4

- 包裹 `_post_edit`（`kuyao_image_edit.py:152-221`），额外 2 次尝试，抖动 1s/4s
- 仅对 `httpx.ConnectError/ConnectTimeout` 与状态码 ∈ `{408, 429, 500, 502, 503, 504}` 重试，遵守 `Retry-After`
- **不要重试 `ReadTimeout`** — provider 已接受请求正在生成，重试会让真实最坏耗时翻倍并重复计费
- 无幂等键，因此 **2xx 之后绝不重试**
- 在 `_generate` 外加模块级 `threading.Semaphore(settings.provider_concurrency)`，避免 A1 把偶发 429 变成系统性 429

**为什么并发后重试更重要**：并发化后，单个 502 就是决定整阶段墙钟的尾巴。

**工作量**：约 2 小时

### A4 — 停止丢弃 provider 错误体 ⚠️ A3 的前置

`kuyao_image_edit.py:179-181` 把响应剥成只剩状态码的 `httpx.Response(status_code)`，
所有失败坍缩成 `KUYAO_IMAGE_PROVIDER_REJECTED` + 一个数字。

**后果**：可重试的 429 与永久失败的内容策略 400 无法区分 —— **不修这个就写不出正确的重试判据**。

修法：读取 ≤8KB，白名单仅 `error.code / type / message`（截断 200 字符）。这既回答了原本「避免回显密钥」的顾虑，又保留了可判定性。`floorplan_vision.py:607-612` 同样处理。UI 侧管道已存在（`AiDesignWorkflow.tsx:735-738`）。

**工作量**：约 1 小时

### A5 — 先实测 `quality=medium`，再决定是否写代码

设 `KUYAO_IMAGE_QUALITY=medium`，跑一批 color_plan，对照实测 p50 93s。**零代码，10 分钟。**

仅当确有显著提速，才把 per-stage `quality` 穿进 `_generate`（`ai_workflow.py:323-340`）：
探索类阶段（彩平/轴侧/风格/色调，N-1 个输出会被丢弃）用预览档，已批准的空间图和局部编辑用 `high`。

顺带修掉 `ai_workflow.py:602` 唯一硬编码的 `size = "1536x1024"`，改用 `_target_size`。

> ⚠️ 这是**假设，不是已验证的结论**。优先级排在 A1–A4 之后。

### A6 — 压缩上传载荷

`_read_input_image` 原样上传 artifact。实测 `floorplan-kuyao-final-*.png` = **2.83 MB → JPEG q88 = 645 KB（4.4 倍）**。
12 空间批次会重复上传 ~60 MB 而非 ~14 MB。

- PNG > 800KB 时转 JPEG q90，长边 ≤1536
- **但语义控制图和局部编辑的红标叠加图必须保持 PNG** —— JPEG 振铃会干扰 `_extract_mark_mask`（`ai_workflow.py:944`）的笔画检测
- 视觉链路同理：`floorplan_vision.py:543` 以 `detail:"high"` base64 原始上传（最大 20 MB → ~27 MB JSON body），降采样到长边 ≤2048，但**仍传原始的 `source_image_width/height`**（`floorplan.py:498`），因为 `_object_scale_estimate` 依赖它们

**工作量**：约 3 小时

## 3. (B) 削减感知等待

### B1 — 增量发布

已包含在第 1 节。**这就是 B 类的主项，不要重复建设。**

### B2 — 计时器 + N/M 计数 + 骨架卡片

零后端改动。`job.createdAt`（`schemas.py:42`）和 `payload.variants`（`schemas.py:38`）已在每次轮询响应里。

- 渲染 `已生成 1分42秒 · 通常需要 3-5 分钟` 和 `已完成 2/4`
- `AiDesignWorkflow.tsx:894` 处放 N 张骨架卡，URL 到达即就地替换

现状：文件里没有任何计时器（`:293` 只有一个 cache-buster），唯一的动效是一个 CSS 脉冲圆点。

> A1 落地后结果网格本身就是进度条，届时只剩计时器和骨架卡有价值。**排在 A1 之后。**

**工作量**：约 3 小时

### B3 — 取消按钮 ⚠️ 必须在第 1 节之后

`POST /v1/jobs/{id}/cancel` 已存在（`main.py:1784`），**前端零调用方**。

需要：`api.ts` 加 `cancelJob`、提交行旁加按钮、`pollJob` 加 `AbortSignal`（现在没有，`api.ts:210-227`）、每个变体循环顶部加 `should_cancel()` 检查（复用第 1 节引入的短会话 helper）。

**诚实的范围说明**：在途的 provider 调用无法中止，只能省下**剩余**变体。而且**今天取消会摧毁所有已生成内容**—— `run_job` 在 `jobs.py:82` 提前 return，还没给 `job.result` 赋值。这正是它必须排在增量发布之后的原因。

**工作量**：约 3 小时

### B4 — 「仅重试失败项」必须合并而非替换结果

按钮横幅承诺「已成功的图片仍会保留」，**服务端也确实只重跑失败项** —— 但 `run()`（`AiDesignWorkflow.tsx:1406-1411`）整体替换了该阶段的 job，画廊只读这一个 job（`:870-871`），于是 3 张已成功的图从阶段视图消失且无法批准。

用户的理性反应是「全部重跑」= 白烧一整批延迟和费用，**纯粹由一个客户端状态 bug 造成**。

修法：按 `variantId` 合并上一批已成功输出后再写入状态。

**工作量**：约 3 小时

## 4. (C) 见真实客户前必须完成的基础设施

### C1 — 重启回收 + 有界关闭 🔴 除第 1 节外投入产出比最高

`jobs.py:74` 置 RUNNING；全仓 `grep '"RUNNING"'` 仅 2 处命中，**没有任何代码回收陈旧行**。
lifespan（`main.py:71-74`）只调 `init_db()`。

- 开发用 `uvicorn --reload`（`scripts/dev.sh:38`），**每次存盘都孤儿化在途生成**
- uvicorn 的 `timeout_graceful_shutdown` 默认 `None`，重启本身会挂起最多 900s 等待 provider 调用，直到操作者 Ctrl-C
- 客户随后轮询一个永久死亡的 job 满 30 分钟，被提示「请点击继续等待」，`resumeWaiting`（`AiDesignWorkflow.tsx:1425-1445`）再轮询 30 分钟

> **卡死是无上限的，不是 30 分钟封顶。**

修法：
- lifespan 中 `yield` 之前执行 `UPDATE jobs SET status='FAILED', error_code='WORKER_LOST' WHERE status IN ('QUEUED','RUNNING')` —— QUEUED 同样重要，因为 BackgroundTasks 要等响应 flush 后才启动
- 加 `--timeout-graceful-shutdown 15`
- 前端遇到 `WORKER_LOST` 显示一键重试

> ⚠️ **约束**：这个无差别 UPDATE 仅在**单进程**下安全。任何人对同一 SQLite 跑 `uvicorn --workers N` 之前，必须先用环境变量开关或 per-process owner 列加以限制。

**工作量**：约 2 小时

### C2 — 结构化日志 + 逐调用计时 ⚠️ A5 的前置

`grep 'logger|logging|print('` 扫 `jobs.py` 和 `main.py`：**零命中**。`Job` 表没有 `started_at` / `finished_at`。

**你现在无法事后区分「N 次串行」「单次尾延迟」「线程排队」。**

- `jobs.py` 加 logger，`jobs.py:77` 前后加 `perf_counter`
- 两个异常处理器（`:94`、`:106`）改用 `logger.exception` —— 现在 traceback 被完全销毁
- `Job` 加可空 `started_at` / `finished_at` 列
- `edit_floorplan_image:512` 返回的 dict 里带上单次耗时

**这是把 A5 和 A3 的重试率假设变成数据的唯一途径。**

**工作量**：约 2 小时

### C3 — 拆分终态事务 + 开启 WAL

`jobs.py:84-93` 先 flush `job.result`，再调 `ensure_scene_asset`（一次 SELECT + 可能的 INSERT，`assets.py:490`），最后 commit。

**该段任何异常 → `except Exception` → `session.rollback()` → 整批已付费的图被丢弃，job 标记 FAILED 且 `result=None`。**

修法：
- 先提交 `result` / `SUCCEEDED`，再在新事务里创建资产；失败时保留 job 为 SUCCEEDED（`backfill_scene_assets` 已存在）
- 同一 PR：`database.py:20-24` 加 `connect_args={"timeout": 30}` 和 `PRAGMA journal_mode=WAL; busy_timeout=30000` —— **今天没有 WAL，每个写入都阻塞 1 秒一次的轮询**
- 顺带把取消竞态改成条件更新 `UPDATE ... WHERE status='RUNNING'`

**工作量**：约 2 小时

### C4 — 独立作业线程池

14 处 `background_tasks.add_task(run_job, ...)` 全部走 anyio 的进程级 `CapacityLimiter(40)`，与每个同步 `def` 路由共享 —— 包括 1Hz 的 `get_job`（`main.py:1748`）、`health`、`cancel_job` 和 StaticFiles 的 `/artifacts` 查找。

**诚实的阈值**：需要约 **40 个并发 RUNNING 任务**才会耗尽，不是「几个客户」—— 一个 job 无论多少变体都只占一个线程。所以这**不是当前的客户故障**，而是一个没有背压的悬崖。

修法：`jobs.py` 里换成模块级 `ThreadPoolExecutor(max_workers=8)`。

> A1 的内层 executor 线程是普通线程，**不消耗 anyio 令牌**，因此 A1 不会放大这个问题，也不需要调高 anyio 上限。

**工作量**：约 2 小时

### C5 — 建任务 POST 的幂等键

`xhrRequest`（`api.ts:59-89`）在 `onerror` / `ontimeout` 时**对所有方法**自动重试两次，包括全部 6 个建任务 POST —— **一次丢失的响应会静默启动第二个完整的 N 变体批次**，墙钟和费用双双翻倍。

修法：`Job` 加可空唯一列 `idempotency_key`，前端每次用户提交生成 `crypto.randomUUID()`，冲突时返回既有 job。

> **不要简单地关掉 POST 重试** —— 多 MB 上传恰恰是响应丢失最容易发生的地方，重试在那里是真实的韧性。

**工作量**：约 4 小时

### C6 — 磁盘空间预检

`.local/artifacts` 现在 **834 文件 / 635 MB**，`app/` 下**没有任何删除路径**，且与 SQLite 数据库同一文件系统（`config.py:15-16`）。磁盘写满会同时破坏图片写入和事务提交 —— 而按 C3，提交失败会丢弃已付费的批次。

过渡方案：启动时记录可用空间，低于阈值拒绝启动任务，让失败发生在计费之前。完整的保留策略见 D2。

**工作量**：30 分钟

## 6. 顺序约束

1. **A4（错误体）→ A3（重试）** —— 两者都坍缩成同一个不透明错误码时，无法编写 429 vs 400 的分支判断
2. **A2（共享客户端）+ A3（重试 + 信号量）→ A1（并发）** —— 没有客户端并发上限和退避就并发，会把偶发 429 变成系统性 429
3. **第 1 节增量发布 → B3（取消）** —— 否则取消按钮会把「变体不对」变成「什么都没有」
4. **第 1 节 → B2（进度 UI）** —— A1 之后结果网格本身就是进度条，只剩计时器和骨架卡有价值
5. **C2（计时日志）→ A5（质量档位）** —— 不要发布一个你无法度量的质量降级
6. **C1 的无差别 UPDATE → 任何迁往 `--workers N` 的动作** —— 先确保单进程
7. **D2 内容寻址 → D2 保留策略** —— 共享路径会让 mtime 淘汰出错
8. **C4 不阻塞 A1** —— 内层 executor 线程绕过 anyio 限流器

### 建议执行顺序

```
A4 → A2 → A3 → A1(+增量发布)      ~2-3 天   ← 全部用户可见的提速都在这里
C1 → C2 → C3                      ~1 天     ← 见真实客户前的最低门槛
B2 → B4 → B3                      ~1 天     ← 感知优化与数据安全
A5(先实测) → A6 → C4 → C5 → D 类
```

## 7. 明确不建议现在做的

| 不做 | 理由 |
|---|---|
| **上 Redis / arq / RQ / Celery 队列** | 这是**正确的最终答案** —— BackgroundTasks 确实不是作业系统，重启后什么都不留。但 C1 用约 2 小时就把唯一的用户可见症状（永久卡死）转成可重试失败，而 retry 端点已经存在。**现在该做的是把 14 处 `add_task` 收敛到一个 dispatch helper**（随 C4 一起），将来替换队列就是改一个文件。等到跑多进程、或需要任务跨部署存活时再迁移 |
| **生成结果缓存** | 不是免费优化。按 source+prompt+model+size+quality 做键，意味着用户重新提交未改动的阶段会拿到**逐字节相同**的图 —— 这等于从一个**生成式**产品里删掉「重摇一个样本」。彩平 / 风格 / 空间图恰恰是用户最想 re-roll 的地方。**这是产品决策，不是性能修复** |
| **关掉前端 POST 自动重试** | 会牺牲多 MB 上传场景下的真实韧性。要么做幂等键（C5），要么什么都不做 |
| **`n>1` 批量参数** | 结构上无法帮助当前循环 —— 每次迭代 prompt 都不同 |
| **prompt / semanticLayout 瘦身** | 实测 8.7–21.5 KB，去掉 `polygon` 只省 11%，walls 占大头，没有廉价的裁剪空间。**替代做法**：加一个 28,000 字符的硬断言抛出清晰的 `INPUT_REJECTED`，让超大户型可操作地失败而不是收到不透明的 400。5 行代码，随 A4 一起发 |
| **HTTP/2** | `h2` 未安装，且对「每连接一请求」的负载毫无收益 |
| **三重缓冲重写** | 在 ~15-20 MB/次的规模下无害；只有当 12 路并发暴露内存压力时才重新评估 |
| **`busyStage` 改成 Set** | A1 落地后大部分冗余：重叠两个阶段只省 min(t_axo, t_space) ≈ 30-40%，而变体级并发已经吃掉了大部分收益。而且还需要把 `run()` 的 `finally { setBusyStage(null) }`（`:1421`）改成集合删除，否则先完成的阶段会为仍在运行的另一个阶段解锁提交按钮 |
| **切 Postgres** | SQLite + WAL（C3）在当前负载下够用。多进程时再评估 |
| **把 `JOB_WAIT_TIMEOUT_MS` 降到 10 分钟** | 已经可以通过 `VITE_JOB_TIMEOUT_MS` 覆盖；C1 之后 30 分钟的卡死会变成即时的 `WORKER_LOST` 失败，这个超时值就不再重要了 |

## 8. 审计过程中对初审结论的修正

对抗性验证推翻或修正了以下说法，记录以免重复讨论：

- `add_task(run_job, ...)` 是 **14 处**（grep 验证），不是初审说的约 28 处
- 线程池饥饿需要约 **40 个并发任务**，不是「几个客户」就会触发
- **`n>1` 无法修复串行循环**（每次迭代 prompt 不同）
- 并发收益是 **max-of-N**，因此每阶段预期 **2.5–3 倍**，不是朴素的 4 倍
- 重启卡死是**无上限**的，不是 30 分钟封顶（`resumeWaiting` 会再轮询 30 分钟）
- 「无分批结果」的修复是**纯后端**的：`pollJob` 的 `onUpdate` 已经每秒回调完整 job，前端渲染路径已支持
